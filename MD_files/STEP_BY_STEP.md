## How we work (the priority is understanding the backend)

From SPEC.md: *"In the follow-up interview we will ask you to modify this code live and explain
your choices, so make sure you understand what you have built."*

So the **backend** is built in small steps, and every backend step ends with the same five-part loop.
The **frontend** is generated in one go and gets a short tour only.

```
 ┌─ 1. BUILD ──────── Claude writes the step's files (small, readable, no clever tricks)
 │  2. WALKTHROUGH ── Claude explains every file top to bottom: what each function does, why it
 │                     exists, what calls it, and the request flow through it. You ask anything.
 │  3. CHECK ──────── You answer the step's "explain it back" questions in your own words
 │  4. DRILL ──────── You make one small live change (like the interview), run it, then revert or keep it
 │  5. LOG + COMMIT ─ Update the named BUILD_LOG.md sections, write MD_files/build_logs/step-N-<name>.md
 │                     (detailed explanation of the step), then make the commit listed for the step
 └──────────────────── Next step starts only after you say "go"
```

**Rules**
- **BUILD_LOG.md is filled as we go, never at the end.** Every step names the exact template sections
  to update ("📝" lines). Things that broke and AI mistakes are written down *when they happen*.
- **Commit after every step** (7 commits, table below), using the message given. Messages describe
  intent, not mechanics. Never `git add .env`: `.gitignore` is written before the first commit.
- **Keep the template.** BUILD_LOG.md keeps the provided headings exactly as they are; we only fill them in.
- **Timebox:** building is about 2 h (SPEC). Walkthroughs and drills add about 30–40 min on top.
  Understanding the backend comes first, so that time is well spent. The frontend and polish get cut first.

## Step 2: Scoring rules, pure Python (backend, deep: the heart of the interview)

No LLM yet. The number is computed from verdicts, so we build and understand the maths first,
using hand-made verdicts.

**Build**
- [ ] `backend/schemas.py`: `Verdict`, `Criterion(id, tier, text)`, `CriterionVerdict`, `Finding`,
      `LLMEvaluation` (§5.3).
- [ ] `backend/agents/scoring.py` (§5.4), kept short. **You write or rewrite parts of it yourself**
      (BUILD_LOG asks for "something you wrote yourself"):
  - constants `TIER_WEIGHTS`, `VERDICT_POINTS`, `GATE_CAP = 30`
  - `normalise(text)`, `check_evidence(verdicts, vendor_text)`, `compute_score(criteria, verdicts, vendor_text)`
- [ ] `experiments/scoring_sanity.py`: 4 hand-made cases (all met → 100; mandatory not_met → ≤ 30;
      made-up quote → downgraded; all not_applicable in one tier → weight redistributed).

**Walkthrough**
- Each constant and what changing it does to vendors A, B and C.
- `compute_score` line by line, with a worked example on paper: vendor A vs RFQ-001 → raw ~78 → capped 30.
- The quote check: what it catches (invented quotes) and what it can't (vague but real quotes, which

- Why this file has no I/O and no LLM (pure function: same input → same score).

**Check: explain it back**

2. Why is `not_applicable` removed from the average instead of counting as 0?
3. What happens if the LLM forgets to return a verdict for `R2`?
