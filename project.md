## 3. What to build (from SPEC.md)

Single-page app, no routing, no auth, no deployment.

1. RFQs stored in a database, seeded with the three provided.
2. User picks an RFQ from a dropdown.
3. User pastes or uploads a vendor profile (plain text).
4. Backend invokes an AI agent — **exactly one LLM call per evaluation**.
5. UI shows: **score out of 100, 3 supporting reasons, 2 gaps**.
6. Past evaluations listed below, most recent first.

**Deliverables:**
1. Public GitHub repo with the working app.
2. README that works on a clean clone: setup, env vars, how to load seed data, how to run.
3. `BUILD_LOG.md` in repo root, filled in from the template.
4. ≥ 5 meaningful commits, messages describing intent — no single squashed commit.
5. (Optional) AI session transcript.

Also required: secrets only in env vars; seed data loads via a documented command or on first run.

**Out of scope:** RAG, vector stores, multi-agent orchestration, ranking vendors against each
other, styling beyond legible, tests, CI/CD, document-parsing edge cases.

**Timebox:** ~1.5–2 h. "We evaluate approach and clarity, not features." In the follow-up
interview they will ask for **live modifications** — every line must be understood.

## 4. What's actually being tested — the sample vendors are traps

The key BUILD_LOG question: *"What did you do to make that number mean something?"*

| Vendor | Profile | The trap |
|---|---|---|
| **A — Sundar Precision** | Technically excellent for RFQ-001: 5-axis DMG MORI, ±0.01 mm (beats ±0.02), Ra 0.8 (beats Ra 1.6), 2 in-house Zeiss CMMs, AS9102 FAI reports, heat-lot traceability, free-issue material experience, 4–5 wk lead time, 70% utilisation. **But only ISO 9001 + IATF 16949 — no AS9100D.** No aerospace customers (automotive, medical). | **Fails RFQ-001's mandatory.** A naive "rate out of 100" gives ~85. A meaningful score disqualifies or caps it. |
| **B — Arcline Aerospace** | **Has AS9100D** (passes mandatory). Fails almost everything else: no 5-axis, ±0.05 mm, Ra 3.2, CMM outsourced (+2–3 days), 9–11 wk lead vs 6 wk, largest order 120 vs 250 needed, 90% utilised, only 2 small 7075 prototype jobs. | Passes the gate but can't make the part. Forces a decision: should a vendor failing hard technical specs outscore one missing a certificate? |
| **C — Vector Industrial** | Pure marketing copy. Claims machining + coating + raw material. **Names no certificate, machine, tolerance or customer.** "Aligned with international aerospace standards" ≠ AS9100D; "work closely with accredited partners" ≠ NADCAP. No employee count, no founding year. | Rewards-claims-without-evidence test. Should score low against **all three** RFQs even though it "matches" all of them. |

Also:
- **Cross-category:** A or B vs RFQ-002 (coating) or RFQ-003 (titanium supply) should be near zero.
- **Numeric traps:** lower Ra is better (0.8 meets 1.6; 3.2 fails it) — LLMs often invert this.
- **Lead-time basis:** Vendor A's 4–5 weeks is "from receipt of material"; material is
  free-issue (customer-supplied), so not directly comparable to "6 weeks from PO".

**Expected shape of results (sanity check, not exact numbers):**

| | RFQ-001 | RFQ-002 | RFQ-003 |
|---|---|---|---|
| A | low-mid (gate fails, strong otherwise) | near zero | near zero |
| B | low-mid (gate passes, technicals fail) | near zero | near zero |
| C | low (nothing evidenced) | low | low |

Run all 9 combinations before calling it done; the table goes into BUILD_LOG as evidence.

## 5. Where the spec is unclear (BUILD_LOG material)

Log each with the assumption made:

- **RFQ-002 "Parts up to 600 mm" appears twice in the JSON** — in `technical` *and* `preferred`.
  The `.md` has it only under Preferred. Hard spec or preference? Naive scoring double-counts it.
- **RFQ-003 duplication** — "Cut-to-size capability" (technical) and "Ability to supply
  cut-to-size" (required).
- **JSON vs Markdown differ** — RFQ-002 `.md` has no Technical section; `+/-` vs `±`.
  Assumption: `rfqs.json` is the source of truth.
- **"Exactly 3 reasons / 2 gaps"** — what if a vendor has no genuine strengths (C) or no real
  gaps? Decide: always return exactly 3/2, phrasing weak items honestly.
- **"AI agent" + "one LLM call"** — no agent loop and no retry on malformed output. The "agent"
  is one structured call. State this explicitly.
- **Past evaluations** — all of them, or filtered to the selected RFQ? (Default: all, newest
  first, showing RFQ id + vendor.)
- **"Uploads or pastes"** — decide whether upload is a separate backend path. (Default: read
  the `.txt` client-side into the textarea → one backend input path.)
- **SPEC typo** — "~1.5 tp 2 hours".

## 6. Scoring design (the core of the assignment)

**Principle: the LLM judges each requirement; code computes the number.**

One LLM call (forced tool call / structured output), temperature 0, returns:
- Per RFQ criterion (technical, quantity/delivery, mandatory, required, preferred):
  `verdict: met | partial | not_met | not_evidenced` + short **verbatim evidence quote** from the
  vendor profile + one-line rationale.
- 3 reasons and 2 gaps, each referencing a specific criterion.

Deterministic Python afterwards (`backend/agents/scoring.py`):
1. **Evidence check** — each quote must appear (normalised substring) in the vendor text;
   otherwise downgrade to `not_evidenced`. Cheap anti-hallucination guard, no second LLM call.
   This is what sinks Vendor C.
2. **Weighted score** — e.g. technical+delivery 40, required 35, preferred 25;
   `met = 1.0`, `partial = 0.5`, `not_met / not_evidenced = 0`.
3. **Mandatory gate** — any mandatory criterion not `met` caps the score (see §9 decision).
4. **Dedupe** duplicate criteria (RFQ-002 600 mm, RFQ-003 cut-to-size) before weighting.
5. **Persist** verdicts, raw LLM output, model id and a `PROMPT_VERSION` with every evaluation.

Keep `scoring.py` a small pure function — easiest to defend and the most likely target of
"change the weights live". Candidate for writing by hand (BUILD_LOG: "something you wrote
yourself rather than generated").

## 9. Decisions (resolved 2026-09-28)

1. **Stack** — Python + FastAPI; minimal TypeScript frontend (Vite, no framework); SQLite at
   `data_warehouse/astrobase.db`; **OpenAI via LangChain** (`langchain-core` + `langchain-openai`);
   prompts in `backend/prompts/`. `model.py` stays the provider seam.
2. **Mandatory gate** — **cap at 30**, so "missing one cert" still differs from "fails everything".
2b. **Docker** — `backend/Dockerfile` + `frontend/Dockerfile` + `docker-compose.yml`; local startup and
   testing via `docker compose up --build` (reverses the §7 "delete docker-compose.yml" note).
3. Found in review: the verbatim-quote check alone does NOT sink Vendor C (its vague sentences are
   real quotes) — the prompt's specificity rule carries that. Added a `not_applicable` verdict for
   criteria whose precondition doesn't exist. IATF 16949 / ISO 9001 ≠ AS9100D stated in the prompt.
